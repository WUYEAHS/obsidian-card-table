# 回顧(self-review / dreaming)

目的:同一個錯不要犯第二次,而且讓使用者看得到我學到什麼。

**節奏(使用者明講,2026-09-18)**:
- 完整的回顧只在**大版本的一輪結束時**寫(例:1.6 → 1.7)。小的一輪(例:1.6.2)有值得講的才寫,沒有就不寫。
- 平常要**更頻繁、更短地**跟使用者講:每做一件事,在 vault 的 `0.常用/Card table project/Dev chat.md` 最下面留一兩句
  (像 Discord:發現了什麼、做了什麼、需要使用者什麼),使用者直接在底下回。回顧時再把 Dev chat 裡有價值的整理起來。
- 回顧要有彈性:每一版的挑戰不一樣,段落可以增減,不要為了填滿範本硬寫。

## 收集(只讀)

1. `git log --since="<今天> 00:00" --stat` 和 `git status`(還沒 commit 的改動)。
2. vault `0.常用/Card table project/` 今天改過的文件:Dialogue 的新留言和使用者的回覆、PRD、CR、Review pack。
3. 這段對話裡:使用者糾正我的地方、白做的工、失敗的測試、環境的意外(例如外掛資料夾換了位置)。
4. 上一篇回顧的「下次怎麼做」:這次做到了沒有。

## 寫成一篇

- 路徑:`0.常用/Card table project/Reviews/YYYY-MM-DD review.md`。同一天第二次,就接在同一篇後面(`## 第 2 段`)。
- 範本:`Procedure/Templates/Template - Daily review.md`。段落:
  - 今天做了什麼(連到 Dialogue 的代號或 PRD 編號)
  - 做對的(要保持)
  - 做錯或差點做錯的:**現象 → 根因 → 下次怎麼做**,一條一條寫
  - 上次的「下次怎麼做」有沒有做到
  - 要問使用者的
  - 缺的知識或技能:先用技能搜尋工具(SearchSkills)或 GitHub 的 `anthropics/skills` 找。**列給使用者看,不自己安裝。**
- 寫完把連結加進 `Main navigator.md` 的「回顧」。

## 把學到的東西放回去

- **我自己的做法**(例如「部署前先問 Obsidian 外掛在哪個資料夾」):直接寫進 CLAUDE.md 對應的段落,或寫進技能。
- **產品規則、使用者偏好**:先在回顧裡列成「建議寫入」,使用者同意之後才寫(標「使用者明講」)。
- **跨專案的教訓**:寫進記憶(memory)。
- 同一個教訓出現**第二次**才升格成 CLAUDE.md 的規則,不要每篇回顧都改 CLAUDE.md。

## 語氣

誠實、具體、短。不寫「今天很順利」這種話。沒發現問題就寫「沒有發現」,不要硬湊。
