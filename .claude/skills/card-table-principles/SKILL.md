# Card Table 統一原則

這九條是判斷的依據。使用者的新需求跟任何一條衝突時,**先講出衝突、提出替代做法、問使用者**,不要默默照做,也不要默默拒絕。
細節規則(寫手、窄螢幕、格式、版本號)在 repo 的 `CLAUDE.md`;路線圖 `docs/roadmap.md` **只是建議,使用者尚未採用**,不能當成已決定的事。

## 九條原則

1. **純文字優先** —— 筆記是唯一的資料;外掛關掉還是一份看得懂的待辦清單。
   格式只加不改;舊寫法永遠照讀、改到才轉;筆記裡的寫法固定一種,不給使用者選(多裝置 / 多人會混寫)。
2. **時間是主軸** —— 功能要回答「今天 / 這週 / 這個月要做什麼」。跟時間無關的功能要有很強的理由。
3. **一個寫入者** —— 所有寫入走 `寫手`:`安全改()` 原子讀改寫、一次動最少的行、寧可不寫也不猜;卡片寫入最後一步是 `蓋卡()`。
4. **跟著 Obsidian** —— 顏色只用 Obsidian 的 CSS 變數(不寫死色碼、不自己偵測深淺)、圖示只用 Lucide(`圖備()`)、快捷鍵用使用者自己的;只做預設主題的深淺兩版。
5. **少色、圖示優先** —— 顏色只給四種意義:分類、逾期、週期、今天;其他一律灰階。能用圖示就不用字,字放在 title / aria-label。
6. **手機是一等公民** —— 手機有自己的 DOM 和版面(`this.窄`),桌機的東西不能硬塞進去;不用 CSS media query。
7. **介面裡能改的,設定頁就不放** —— 設定頁照大標分組(更新內容 → 一般 → 時間篩選 → 卡片外觀 → 新增與編輯 → 動作後跳轉 → 筆記格式 → 支持),新設定放進對應的大標。預設值要好到多數人不用開設定。
8. **每一版都講得清楚** —— 更新介紹彈窗、版本摘要、CHANGELOG 三處一起寫;README 精簡(每個大項 2–3 句)。
9. **先畫、再做、再量** —— 版面先在 Figma「Card Table UI」定案(使用者在 Figma 留言);實作後 `tools/check4.ps1` 六組全空、`tools/run-tests.ps1` 全過,才發版。每一版只有一個主題。

## 怎麼用

收到需求時,依序回答:

1. **這是哪一類?** 功能 / 版面 / 格式 / 設定 / 文件。
2. **碰到哪幾條原則?** 逐條列出「符合 / 衝突 / 不相關」,只寫有關的。
3. **有衝突就停下來問**:說清楚衝突在哪、可能的後果(例如「格式改了,舊版外掛讀不懂」)、兩三個替代做法,並標出建議。
4. **沒有衝突,列出要一起做的事**:
   - 格式或寫入 → 用技能 `card-table-format-test`(先補測試案例)。
   - 版面 → Figma 先定案;改完跑 `check4.ps1`;必要時用 `design-review` / `better-interface`。
   - 新流程(沉浸模式、手機新增…)→ 先用 `ux-flow-designer` 畫流程。
   - 格式或架構的取捨 → `adr-writer` / `tradeoff-analysis-writer`。
   - 要發版 → 技能 `card-table-release`。
5. **記下使用者的決定**:明講的規則寫進 `CLAUDE.md` 對應的段落(標「使用者明講」),不要只留在對話裡。

## 常見的衝突(以前真的發生過)

- 想在第一行加一個新標記 → 原則 1:只加不改,舊寫法照讀;加之前先定好名字(`[key:: value]`)。
- 想用寫死的顏色讓某個東西「比較顯眼」 → 原則 4、5。
- 想在設定頁加一個開關微調版面 → 原則 7:先問能不能在介面上直接改,或乾脆選一個好的預設。
- 想用 `@media` 或 `!important` 修手機 → 原則 6 與 CLAUDE.md 的窄螢幕規則。
- 同一版同時改格式、版面、設定 → 原則 9:拆成不同版本。
